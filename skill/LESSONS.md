# 经验总结：方法论与踩坑（可迁移）

> 这些不是这一个探头的专属知识，而是**任何"用逻辑分析仪逆向一个未知私有协议"**都适用的经验。
> 每一条都真实浪费过时间。

---

## A. 逆向未知私有协议的标准流程（本项目验证有效的顺序）

1. **先定物理层，别急着猜协议。**
   看**最小游程**判定位宽：本例最小游程 104 µs ⇒ 9600 baud（一位 104.17 µs）。
   看到 **937 µs 的簇 = 9 位 = 一整个 8N1 帧**，就直接确认了帧边界。
   先试常见波特率扫一遍，比盯着波形猜快得多。
2. **多根线先分方向。** 哪根是主机发的、哪根是设备回的？
   判据：**内容恒定的那根是命令，随读数变化的那根是数据**。
3. **按帧头切帧，做"逐字节 uniq 统计"。** 一次列出"哪些字节在变、变多少种值"，
   立刻把"结构"和"数据"分开。工具：`tools/uart-frames.cjs`。
4. **扫所有 4 字节窗口，找"在所有帧里都是合理浮点数"的字段。** 工具：`tools/uv-analyze.cjs`。
5. **给每个候选字段建立"物理动作 → 数值变化"的对应。** 这是唯一能把语义钉死的方法。
6. **最后反推校验和。** 穷举 65536 个多项式，比猜算法快得多。工具：`tools/checksum-hunt.cjs`。

## B. 用仪器自己的显示屏当权威参照（本项目最关键的一招）

协议逆向最容易"自我说服"。**仪器自己的显示屏是免费的、独立的权威参照。**

做法：让某个字段的**计算值**与**屏上读数**做**逐位对照**：
```
帧内 f6 峰值 3284.0359  ↔  表显最大值 3.2840        ✓ 逐位吻合
帧内 f6 峰值 3286.2664  ↔  表显最大值 3.2863        ✓ 逐位吻合
帧内 f6 峰值 3290.4019  ↔  表显最大值 3.2904        ✓ 逐位吻合
```
三轮、四位小数、无一例外 —— 这种强度远超任何统计推断。
**并且要主动请用户抄屏**（用户知道屏上有什么，AI 不知道）。

## C. 让激励可控：自制信号源 > 找现成光源

本来要"用紫外灯照探头"，一度卡在**可见光完全无响应**上。
最后改用**同款 F103 + 共阳 RGB LED** 做**波长可控、时序精确**的激励源：
固件自己写、自己烧、自己复位 —— **激励端与采集端都在 AI 手里**，不需要用户掐时间。

配套两个设计要点：
- **留"周期标记"**：循环里安排一段明显更长的熄灭（本例 12 s），
  这样"响应落在哪个相位"可以**只从数据反推**，不依赖两端时钟对齐。
- **单次脉冲模式**：用于"清零记录 + 测一次"这类需要干净基线的实验（不循环，避免污染最大值）。

## D. 双方向都要交叉验证

任何"X 就是 Y"的结论，至少用**两条独立路径**验证：
- 校验和：**两轮独立抓取**都命中同一条算法 + **两条不同命令**的末两字节交叉验证；
- 单位：**表显对照**（3 轮） + **切到另一单位档后帧内数值不变**；
- 最小值：清零命令后跳成当前读数 + 长期为 0 时与表显 `P_MIN 0.0000` 一致
  + "**最大值不可能长期为 0**"这条逻辑判据；
- 平均值：稳态下与瞬时值相等（差 0.4%）。

## E. 踩坑清单（每条都真实浪费过时间）

### E1. 逻辑分析仪"打不开"≠ 驱动问题 ★最大的时间黑洞
症状：`LIBUSB_ERROR_NOT_SUPPORTED`，但 `--scan` **能列出设备**。
**`libusb_open()` 不做任何 USB 通信**，纯按注册表元数据派发后端 ⇒
与接线/供电/固件/驱动**无关**。
根因：sigrok 的 Windows 构建（**含最新 nightly**）都静态链接同一个 2016 年的
`libusb 1.0.20.11003-rc3`。**重装驱动/删驱动包/重启/换口全部无效。**
**正解：绕开它，用官方新版 libusb 自己抓**（`tools/fx2cap.cjs`）。

### E2. fx2lafw **没有 STOP 命令** ⇒ 抓取前必须 USB 复位
协议里只有 `GET_FW_VERSION / START / GET_REVID`；主机一停读，FX2 的 FIFO 填满就卡死，
表现为"**只发一包然后全是 timeout**"。**每次抓取前 `libusb_reset_device`。**

### E3. 直接 kill 抓取进程 = 丢掉全部数据
采样缓冲只在结束时写盘。开放式长时间抓取要用**停止文件**机制（`--stopfile`）。

### E4. 忘接分析仪的 GND ⇒ 8 通道全部悬空读高
"全部通道 0 边沿、恒高"**不是协议问题**，头号嫌疑是**分析仪没有参考地**。
**判据**：用 SWD 读目标的 `GPIOx_ODR` 确认目标真在跑（本例读到 `0x5010` ⇒ 蓝灯确在亮）
⇒ 目标正常 ⇒ **去查分析仪侧接线，而不是继续查协议**。

### E5. 基于边沿的 UART 解码脚本会被 **1 采样宽的毛刺**骗
一段**完全合法的 8N1** 被解成乱码（本例 D0 被误判成 `AB 02 14 89 F0`）。
**怀疑解码器之前，先打印原始游程核对**（`tools/runs.cjs`）——
手工按位数一读就发现信号是完美正确的 `AB 20 60 00 14 00 89 07`。

### E6. STM32 USART 的 **BRR 公式**
`USARTDIV = fCK / (16 × baud)`，**BRR = (mantissa << 4) | fraction**。
115200 @ 8 MHz 应为 **`0x45`**（写成 `0x457` 会变成 ~7200 baud）。
9600 @ 8 MHz 是 `0x341`。

### E7. **采样率必须 ≥ 波特率 × 10**
115200 baud 在 250 kHz 采样下只有 **2.2 采样/位**，解不出来（表现为全是碎片字符）。
**要么降波特率、要么提高采样率。**

### E8. 单传输同步读法撑不住高采样率
8 MHz / 16 MHz 时 FX2 只发一包就停（隐含采样率掉到 127 kHz）。
libsigrok 用的是 **32 路并发传输**；要跑高速率得改成多路并发。

### E9. 表在**设置模式下不轮询探头**
表现为"改了设置但线上毫无变化"。**真正值得观察的是"退出设置、回到测量界面"那一刻**
（表会在这里把配置下发给探头）。

### E10. 固件的"信号突发占空比"要和抓取窗口匹配
主循环周期 ~170 ms、突发只占 ~2.5 ms 时，100 ms 抓取大概率一次都撞不上，
现象和"固件根本没发"**一模一样**。—— 做这类验证一开始就把循环周期做短。

### E11. openocd 的两个坑
- `echo 裸词 [mdw ...]` 会让整个会话**静默退出**（无报错）；必须 `echo [mdw ...]`（方括号紧跟 echo）。
- 引号内 `\` 被当转义符 ⇒ 路径**一律用正斜杠**。
- PowerShell 调用要用 `& $openocd @args`（数组传参）；`Start-Process -ArgumentList` 数组**不带引号**，
  会把 `echo [mdw ...]` 拆开。

### E12. PowerShell 5.1：原生程序写 stderr + `$ErrorActionPreference='Stop'` = 假故障
第一行 stderr 就抛 `NativeCommandError` 并中断脚本，**重定向文件却是空的**。
调原生程序前后临时切 `'Continue'`，再显式查 `$LASTEXITCODE`。

### E13. 中文输出被编码搞坏
`Start-Process -RedirectStandardOutput` 写 UTF-8，`Get-Content` 默认按 GBK 读 ⇒ 全成乱码。
**读的时候加 `-Encoding UTF8`**，或让脚本**只输出 ASCII**。

## F. 交接纪律（给下一个智能体）

1. **别只信文档，先跑一遍工具链**（`captures/` 里有现成样本，无需硬件）：
   ```powershell
   node tools\uv-analyze.cjs captures\ls125-dark-3s.bin 1000000 2 9600
   ```
   能复现出"帧长 28、f6/f10/f22 三个浮点字段"就说明环境和工具都正常。
2. **要改协议结论，必须给出新的实测证据**（新抓取的字节、或表显对照），
   不能靠推理推翻。本文所有结论都有验证方式标注。
3. **动硬件前先想清楚"谁在驱动哪根线"**：自制主机和原装表**不能同时接**在同一根信号线上。
4. **每次抓取前确认分析仪 GND 已接**（踩过一次，白花十几分钟）。
